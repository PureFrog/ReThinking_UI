# ReThinking_UI 협업 지침서

**버전** 2.0 · 2026-10-28
**대상**: 사용자(PureFrog), Claude(개발), ChatGPT(이미지 제작·기능 QA)
**저장소**: https://github.com/PureFrog/ReThinking_UI

이 문서는 **무엇을 만들지**가 아니라 **누가, 어떤 순서로, 어디에 결과를 남기며 함께 일하는지**를 정한다. 무엇을 만들지는 `docs/ux-spec.md`가 정한다.

---

## 0. 우선순위와 읽는 순서

판단이 부딪히면 위에 있는 것이 이긴다.

1. **사용자의 결정** — 특히 화면을 보고 느낀 감각("별로야", "답답해")은 어떤 문서보다 우선한다.
2. **`CLAUDE.md` / `AGENTS.md`의 절대 규칙** — 모의 데이터만, 투자 권유 금지, 비밀값 금지 등.
3. **`docs/ux-spec.md`** — 화면·기능·인터랙션 명세. 특히 11장(통일 규칙), 11.16(금지 목록), 13장(작업 순서).
4. **이 문서** — 협업 절차.
5. **`docs/handoff.md`** — 옮겨오기 전 GPT 프로토타입의 현재 동작. 참고용.

새로 합류하는 에이전트는 이 문서 → `ux-spec.md` 13장 → 11장 순서로 읽는다.

## 1. 프로젝트 맥락 — 모든 에이전트가 알아야 할 것

**무엇인가.** '마음이 자라는 정원'. 사용자가 캐릭터로 아이소메트릭 집과 정원을 돌아다니며, 주식 보유를 표현한 나무를 돌보고, 놀러 오는 동물 친구(모아·토리·루온)와 유대를 쌓고, 집을 꾸미는 React + Phaser 웹 UI다. 투자 일지·퀴즈·회고 같은 성찰 행동이 정원 성장의 연료다.

**왜 만드는가.** FDS A조 팀 프로젝트 '다시 생각해볼래?'의 사용자 경험 부분이다. 서비스의 목적은 손실 중인 종목의 보유 이유를 투자자가 **스스로** 다시 생각하게 돕는 것이다. 캐릭터는 매매를 권하지 않고 질문한다. 금융 분석 모델(서서히·급락·반박 모델)은 팀이 별도로 개발 중이며, 이 UI에서는 **모의 데이터와 준비된 대사**로 그 결과를 보여주는 자리만 만든다.

**마감.** 팀 프로젝트는 **2026-11-27**에 끝난다. 시간이 한정돼 있으므로, 화려한 자동화보다 사용자가 체감하는 화면 품질에 시간을 쓴다.

**지금까지의 경과.**

- GPT가 ChatGPT Sites 작업 환경에서 프로토타입을 만들었다 (`docs/handoff.md`).
- 사용자는 그 결과를 "감이 없다"고 판단했다. 개선 설계서를 줘도 디자인이 거의 바뀌지 않았고, 말풍선을 누를 때마다 안내 토스트가 반복됐고, 캐릭터가 살아 있지 않았고, 서랍·책장 패널이 별로였고, 아이템을 그림 없이 보여줬고, 일지·퀴즈 성취감 시스템이 빠져 있었다.
- 그래서 **코드는 Claude가, 이미지는 ChatGPT가** 맡는 구조로 바꾸고 저장소를 이곳으로 옮기기로 했다.

**사용자.** 금융·데이터 분석 배경의 학생이다. 개발 전문가가 아니므로, 사용자에게 요구하는 수작업은 최소로 하고 명령어나 클릭 경로를 정확히 알려준다. 사용자와는 한국어로, 짧고 직설적으로 대화한다.

## 2. 문서 지도

새 명세 문서를 늘리지 않는다. 같은 내용이 두 곳에 있으면 반드시 어긋난다.

| 파일 | 내용 | 고치는 사람 |
| --- | --- | --- |
| `CLAUDE.md` | Claude가 매번 읽는 절대 규칙과 작업 방식 | Claude (사용자 승인) |
| `AGENTS.md` | ChatGPT/Codex가 저장소에서 읽는 규칙과 권한 | Claude (사용자 승인) |
| `docs/ux-spec.md` | 화면·기능·인터랙션·에셋 명세. **유일한 명세** | Claude (사용자 승인) |
| `docs/handoff.md` | 이전 프로토타입 동작 기록. 더 고치지 않음 | — |
| `docs/COLLABORATION.md` | 이 문서 | Claude (사용자 승인) |
| GitHub Issues | 에셋 요청, QA 결과, 작업 단위 추적 | 모두 |

GPT 초안의 `PRODUCT_SPEC.md`, `DESIGN_SYSTEM.md`, `COMPONENT_SPEC.md`, `INTERACTION_SPEC.md`, `ASSET_REQUESTS.md`, `QA_GUIDELINES.md`는 **만들지 않는다**. 각각 `ux-spec.md`의 1장, 6장, 9장, 11장, 6장, 11.16으로 이미 있다. 에셋 요청과 QA 결과는 파일이 아니라 Issue로 관리한다.

명세를 바꿀 일이 생기면 `ux-spec.md`를 직접 고치고, 같은 PR에 코드 변경을 넣는다. 예전에 claude.ai 문서로 만든 설계서는 보관용이며, 앞으로는 저장소의 `ux-spec.md`가 기준이다.

## 3. 역할과 권한

| | 하는 일 | 하지 않는 일 | 저장소 쓰기 |
| --- | --- | --- | --- |
| **사용자** | 방향 결정, 화면 확인과 감각 피드백, 에셋 승인, PR 병합, 배포 결정 | — | 전부 |
| **Claude** | 모든 코드, 명세 문서 유지, 에셋 요청 작성, 에셋 통합, 자동 검사, PR 작성, 1차 화면 확인 | 이미지 생성, 사용자 승인 없는 main 병합·배포 | 기능 브랜치, PR |
| **ChatGPT (이미지)** | 에셋 Issue를 보고 이미지 제작, 규격 자체 점검, 납품 | 코드 수정, 명세 변경, 승인 없는 다음 단계 진행 | `assets/*` 브랜치만 (쓰기가 안 되면 사용자가 업로드) |
| **ChatGPT (기능 QA)** | Preview에서 시나리오 실행, 명세 대비 어긋난 점·버그 보고 | 코드 수정, 디자인 결정 | 없음 (Issue·PR 댓글만) |

**ChatGPT QA의 범위를 좁게 둔다.** ChatGPT가 보고할 것은 "명세와 다르다", "동작이 깨졌다", "금지 목록 위반이다" 세 가지다. "더 예뻤으면 좋겠다" 같은 디자인 의견은 **제안** 꼬리표를 붙여 따로 적고, Claude는 사용자 확인 없이 반영하지 않는다. 화면의 감각적 품질은 사용자가 판정한다.

## 4. 시작 절차 — 지금 상태에서 할 일

현재 상태: 저장소는 비어 있고, `setup-docs` 브랜치에 `CLAUDE.md`, `AGENTS.md`, `docs/` 문서만 있다. 코드는 아직 ChatGPT 작업 환경(`/workspace/sites/character-garden`)에 있다.

1. **[ChatGPT] 코드를 main에 올린다.** 기존 git 기록을 유지한 채 `https://github.com/PureFrog/ReThinking_UI`의 `main`으로 푸시한다. `node_modules`, 빌드 결과물, `.env*`, 토큰은 빼고, `public/assets/`와 `tests/`는 포함한다. 원본 기획 문서 `character_garden_service_manual.docx`는 `docs/`에 넣는다. 푸시가 막히면 같은 조건으로 zip을 만들어 사용자에게 주고, 사용자가 Claude에게 전달한다.
2. **[Claude] `setup-docs`를 main에 합친다.** 서로 다른 기록이므로 문서만 얹는 방식으로 합치고, 코드 파일은 건드리지 않는다.
3. **[Claude] 0단계** (`ux-spec.md` 13.3). 구조 파악, `.gitignore`·비밀값 점검, 로컬 빌드 확인, 기준선 스크린샷과 커밋.
4. **[Claude → 사용자] Preview 환경을 정한다.** 기존 빌드는 Sites/Vinext(Cloudflare Worker 계열) 전용 설정이다. Claude가 Vercel과 Cloudflare Pages 중 어디서 최소 수정으로 빌드되는지 확인하고, 필요한 수정과 사용자가 할 클릭을 정리해 제안한다. 사용자가 고르면 연결한다. 기존 chatgpt.site 배포는 더 이상 쓰지 않는다.
5. **[Claude] 최소 CI를 단다.** PR마다 GitHub Actions로 타입 검사·모델 테스트·빌드를 돌린다. 브라우저 자동 테스트(Playwright)는 1~3단계가 끝난 뒤 필요하면 추가한다.
6. **[Claude → ChatGPT] 첫 에셋 요청.** `ux-spec.md` 10장 2단계의 **스타일 시안 1장**(집 일부 + 나무 1그루 + 캐릭터 1명)을 Issue로 요청한다. 코드 1단계(말풍선)는 에셋 없이 진행하므로 이것과 병행한다.

## 5. 한 단계의 표준 사이클

작업 단위는 `ux-spec.md` 13.4의 **단계**다. 한 번에 한 단계만 진행한다.

1. **계획** — Claude가 이번 단계에서 바꿀 것을 3~5줄로 사용자에게 말한다. 사용자가 OK하면 시작한다.
2. **브랜치** — `stage-<번호>-<이름>` (예: `stage-1-bubbles`).
3. **구현** — 필요한 그림이 아직 없으면 도형·CSS 임시 그림으로 진행하고, 에셋 Issue를 연다. 임시 그림도 11.16 금지 목록을 지킨다.
4. **자동 검사** — 타입 검사, 모델 테스트, 빌드. 새 계산 로직에는 테스트를 추가한다.
5. **PR** — 아래 PR 양식대로 올린다. Preview 링크가 생긴다.
6. **1차 확인 (Claude)** — 사용자의 컴퓨터가 연결돼 있으면 Claude가 Preview를 직접 열어 데스크톱 1400px, 모바일 375px 스크린샷을 PR에 남긴다. 못 했으면 못 했다고 쓴다.
7. **기능 QA (ChatGPT, 선택)** — 사용자가 원할 때만 ChatGPT에게 PR 링크를 주고 QA를 시킨다. 결과는 PR 댓글로 남긴다.
8. **사용자 확인** — 사용자가 Preview를 직접 만져본다. 감각 피드백은 Claude가 그 자리에서 고쳐 같은 PR에 다시 올린다.
9. **병합** — 사용자가 OK하면 사용자가(또는 사용자 지시로 Claude가) main에 병합한다. 다음 단계로 넘어간다.

막혔을 때는 같은 방법을 세 번 이상 반복하지 않는다. Claude는 무엇이 막혔는지와 선택지를 사용자에게 바로 알린다.

## 6. 브랜치·PR·Issue 규칙

**브랜치**

| 이름 | 용도 | 만드는 사람 |
| --- | --- | --- |
| `main` | 사용자가 확인한 상태만 | 병합으로만 변경 |
| `stage-<n>-<이름>` | ux-spec 13.4의 한 단계 | Claude |
| `fix-<이름>` | 단계 밖의 버그 수정 | Claude |
| `assets/<묶음 이름>` | 에셋 납품 (예: `assets/style-sample`) | ChatGPT 또는 사용자 |

main에 직접 푸시하지 않는다. 예외는 4장 1번의 최초 코드 이전뿐이다.

**PR 양식** (Claude가 작성)

```markdown
## 이번 단계
ux-spec 13.4의 n단계 — 한 줄 요약

## 바뀐 것
- 사용자가 화면에서 느낄 변화 위주로 3~6줄

## 확인 방법
Preview에서 무엇을 눌러보면 되는지 2~4줄

## 검사
- 타입 검사 / 모델 테스트 n개 / 빌드: 통과·실패
- 화면 확인: 데스크톱·모바일 스크린샷 첨부 또는 "직접 확인 못 함"
- 11.16 금지 목록: 항목별 통과 여부

## 명세와 다르게 한 것
없음 / [제안] 항목을 다르게 구현한 이유
```

**Issue 라벨** — 다섯 개만 쓴다.

| 라벨 | 의미 |
| --- | --- |
| `asset-request` | Claude가 ChatGPT에게 요청하는 그림 |
| `asset-review` | 납품됨, 사용자 승인 대기 |
| `qa` | ChatGPT 또는 사용자가 찾은 문제 |
| `proposal` | 명세에 없는 디자인 제안 (사용자 결정 전까지 작업 금지) |
| `blocked` | 사용자 결정이나 외부 조치가 필요해 멈춤 |

## 7. 에셋 요청과 납품

### 7.1 요청 (Claude → Issue)

에셋 Issue에는 반드시 다음을 쓴다. 규격의 근거는 `ux-spec.md` 6장이다.

- **목록**: 파일명(`캐릭터_동작_방향_번호.png` 형식), 프레임 수, 용도
- **규격**: 캔버스 크기(2배 해상도), 발 또는 밑동 앵커 좌표, 투명 배경, 아이소메트릭 2:1 각도, 왼쪽 위 광원
- **참조**: 승인된 스타일 시안·레퍼런스 시트 경로
- **화면 맥락**: 이 그림이 게임에서 어떤 크기로, 무엇 옆에 보이는지
- **납품 경로**: `public/assets/<폴더>/`와 브랜치 이름

### 7.2 승인 관문 — 순서를 건너뛰지 않는다

1. **스타일 시안 1장** → 사용자 승인
2. **캐릭터별 레퍼런스 시트**(정면·측면·뒷면, 표정 5종, 팔레트) → 사용자 승인
3. **애니메이션 프레임과 나머지 에셋** → Claude가 게임에 넣은 스크린샷으로 사용자 승인

승인은 **사용자만** 한다. ChatGPT의 자체 점검은 규격 확인일 뿐 승인이 아니다. 단독 이미지가 아니라 **게임 화면 안에 넣은 모습**을 보고 승인한다.

### 7.3 납품 (ChatGPT)

- `assets/<묶음 이름>` 브랜치에 파일을 올리고 Issue에 PR 또는 커밋 링크를 단다. 저장소에 쓸 수 없으면 사용자에게 zip으로 주고, 사용자가 GitHub 웹의 Upload files로 그 브랜치에 올린다.
- 같은 캐릭터의 모든 프레임은 승인된 레퍼런스 시트를 참조 이미지로 넣어 만든다.
- 사용한 생성 도구와 약관 확인 결과를 `public/assets/LICENSE_NOTES.md`에 적는다.
- **실제 기업의 로고, 상표, 제품 이미지를 그리지 않는다.** 보유 종목과 연결된 아이템도 업종을 상징하는 일반적인 사물로 표현한다.
- 기존 파일을 덮어쓰지 않는다. 고친 버전은 새 파일명(`_v2`)으로 올리고, Claude가 교체한다.

### 7.4 통합 (Claude)

Claude가 아틀라스로 묶고 에셋 매니페스트에 등록한 뒤 임시 그림을 교체한다. 결과 스크린샷을 Issue에 남기고 `asset-review` 라벨을 단다.

## 8. 기능 QA 규칙 (ChatGPT)

**검수 기준은 일반론이 아니라 이 저장소의 명세다.**

1. `ux-spec.md` 11.16 금지 목록 — 전 항목
2. 이번 단계가 다루는 `ux-spec.md` 장의 규칙 (예: 1단계면 11.2~11.4와 11.11의 시간값)
3. PR의 "확인 방법"에 적힌 시나리오
4. 데스크톱 1400px, 모바일 375px

**보고 양식** — PR 댓글 한 개에 모은다.

```markdown
## QA — PR #번호 / 커밋 SHA 앞 7자리 / Preview 링크

| # | 시나리오 | 기대 (명세 근거) | 실제 | 심각도 | 결과 |
| --- | --- | --- | --- | --- | --- |
| 1 | 친구 말풍선 클릭 | 타이핑 중이면 문장 완성, 안내 토스트 없음 (11.3, 11.16-1) | 토스트 뜸 | High | Fail |

증거: 스크린샷·화면 녹화 링크
확인 못 한 것: (Not Tested 항목과 이유)
제안 (명세에 없음, 사용자 결정 필요): ...
```

**심각도**: Critical = 진행 불가·데이터 손실 / High = 명세·금지 목록 위반, 핵심 흐름 오류 / Medium = 일부 상황에서만 나는 오류 / Low = 사소한 시각 결함.

**원칙**: 실제로 눌러본 것만 쓴다. 검수한 커밋을 반드시 적고, 새 커밋이 올라오면 이전 결과는 무효다. 명세와 다른 점과 개인 의견을 섞지 않는다.

## 10. 모든 에이전트의 금지 사항

1. 실제 금융 데이터, 공시 API, LLM API, 주문·거래, 서버 DB 연결.
2. 캐릭터 대사·화면 문구에 매수·매도·보유 권유나 가격 예측. 캐릭터는 사실 전달, 질문, 사용자가 쓴 이유 되읽기만 한다.
3. 수익률을 보상 조건으로 쓰는 것. 성취는 일지·퀴즈·회고 같은 성찰 행동에만 준다.
4. 토큰·비밀번호·API 키를 코드, 문서, Issue, 출력에 남기는 것.
5. 다른 저장소를 새로 만들거나, 기존 구조를 통째로 갈아엎는 것.
6. 사용자 승인 없이 main 병합, 배포, 공개 범위 변경.
7. 실제 기업 로고·상표 사용.
8. 검증하지 않은 것을 "확인했다"고 보고하는 것. 배포 성공과 화면 확인 완료는 다르다.
